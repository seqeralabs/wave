Wave 1.32.6 was released on March 6, 2026.

## Mandatory steps

Wave 1.32.6 removes SurrealDB entirely: the client, the persistence service, the Surreal to
PostgreSQL migration tooling, and the `surrealdb` environment. Wave 1.32.6 and later can only run
against PostgreSQL.

If your installation still stores data in SurrealDB, **you must migrate to PostgreSQL on Wave
1.32.5 or earlier before upgrading**. The migration tooling exists only in releases 1.21.0 to
1.32.5, so there is no upgrade path from a SurrealDB installation directly to 1.32.6 or later that
preserves your build, scan, mirror and container records.

### Before you start

- A PostgreSQL database reachable from Wave. Wave creates its own tables on startup, so the
  database user needs `CREATE TABLE` and `CREATE INDEX` privileges.
- Redis. The migration uses it for the run lock and to record its progress.
- A backup of your SurrealDB data. The migration only reads from SurrealDB, but take one anyway.
- The [Wave CLI](../cli/index.md), to create the records used to verify the migration.

Add the configuration required by the releases you are passing through, if you have not already:

- `wave.db.uri`, `wave.db.user` and `wave.db.password` for the PostgreSQL connection.
- [Migrating to 1.21.0](./1-21-0.md): `wave.build.logs.path` and `wave.build.locks.path`. These
  replace `wave.build.logs.bucket`, `wave.build.logs.prefix` and
  `wave.build.logs.conda-lock-prefix`.
- [Migrating to 1.24.0](./1-24-0.md): `wave.scan.reports.path`.
- [Migrating to 1.25.0](./1-25-0.md): `-Dio.netty.allocator.type=pooled` in `WAVE_JVM_OPTS`.

### 1. Create records to verify the migration

Run these against your existing installation and keep the IDs. Also record the number of rows in
each of the `wave_build`, `wave_request`, `wave_scan` and `wave_mirror` tables.

```bash
wave --conda-package bwa --wave-endpoint <WAVE_ENDPOINT>
curl <WAVE_ENDPOINT>/view/builds/<BUILD_ID>
curl <WAVE_ENDPOINT>/view/scans/<SCAN_ID>

wave -i ubuntu --config-file <CONFIG_FILE> --wave-endpoint <WAVE_ENDPOINT>
curl <WAVE_ENDPOINT>/view/containers/<TOKEN>

wave --mirror -i ubuntu --build-repo <BUILD_REPO> --wave-endpoint <WAVE_ENDPOINT>
curl <WAVE_ENDPOINT>/view/mirrors/<MIRROR_ID>
```

### 2. Run the migration on Wave 1.32.5

Deploy Wave 1.32.5 with `surrealdb`, `postgres`, `migrate` and `redis` all present in
`MICRONAUT_ENVIRONMENTS`. With `migrate` active, Wave throws
`IllegalStateException: Both 'surrealdb' and 'postgres' environments must be active.` on startup
unless the other two are active as well.

:::warning
PostgreSQL becomes the primary store as soon as Wave restarts with the `postgres` environment
active. Reads and writes go to PostgreSQL from that moment, including the build and scan pages in
Seqera Platform, so records that have not been copied yet are not visible until their table
finishes. Run the migration during a quiet period.
:::

Give every replica the same environments. Only one replica runs the migration — it holds a lock in
Redis, and the others log `Skipping migration since lock cannot be acquired` — but a replica left
with only `surrealdb` active keeps writing to SurrealDB.

The migration starts about 70 seconds after startup and copies the four tables in parallel. It is
complete when all four of these lines appear in the logs:

```console
INFO  i.s.w.s.p.m.DataMigrationService - All wave_request records migrated.
INFO  i.s.w.s.p.m.DataMigrationService - All wave_scan records migrated.
INFO  i.s.w.s.p.m.DataMigrationService - All wave_build records migrated.
INFO  i.s.w.s.p.m.DataMigrationService - All wave_mirror records migrated.
```

Watch for `Error saving <table> record` in the logs. A record that fails for any reason other than
a duplicate key is skipped, and the migration continues — which is why the row counts from step 1
matter.

Optional settings, if the migration runs too slowly or puts too much load on the databases:

`wave.db.migrate.page-size`
: Records fetched per page. Default: 200.

`wave.db.migrate.delay`
: Pause between pages. Default: `5s`.

`wave.db.migrate.iteration-delay`
: Pause between records. Default: `100ms`.

### 3. Verify

Repeat the `/view/` requests from step 1 with the same IDs — all four must resolve — and compare the
row counts of the four tables against the counts you recorded.

### 4. Complete the migration

Remove `migrate` and `surrealdb` from `MICRONAUT_ENVIRONMENTS`, keep `postgres` and `redis`, and
restart Wave 1.32.5. Verify once more, then upgrade to 1.32.6 or later.

Finally, remove the settings that no longer exist: the `surreal.*` block and any
`wave.db.migrate.*` values.

### If you need to run the migration a second time

The migration records its progress in Redis for 30 days, and resumes from it rather than starting
over. If you roll back, or recreate the PostgreSQL database between attempts, delete the
`migrate-surreal/v1:*` keys from Redis before trying again — otherwise the migration resumes from
the old position and the records before it are never copied. Records that are already in
PostgreSQL are skipped when they are sent again, so restarting from the beginning is safe.

If the replica running the migration is killed without shutting down cleanly, its lock is left
behind. Every replica then logs `Skipping migration since lock cannot be acquired` and no records
are copied. Delete the `migrate-lock/v2` key from Redis and restart.
